# AgentBoard 持续自主执行调研与升级路线

> Historical baseline: this research preceded the local 0.4 implementation. See [current autonomous delivery](AUTONOMY.md) and CHANGELOG.md for implemented behavior. No GitHub publication is implied.

调研日期：2026-11-03。本文依据官方仓库、产品文档与工程文章，结合 AgentBoard 本地源码进行比较。竞品功能未经本机实测，不构成“谁是唯一第一”的排名；公开资料也不可能穷尽整个行业。

AgentBoard 的新目标是：用户说明目标和边界后，系统能持续安排工作、执行、检查、修复并交付证据。Codex 可以作为主要执行器，减少人工看守优先于节省 Codex 用量。此文是设计与实施建议，未实现的部分均保留为计划。

## 值得参考的系统

| [Devin 管理多个 Devin](https://cognition.com/blog/devin-can-now-manage-devins) | 协调者拆分任务，执行者在独立环境中工作，协调者处理进度和冲突 | 同一 Codex 登录下可设计不同会话承担规划、实现和审查；先做可靠串行，再增加可控并行 |

| [OpenHands SDK](https://github.com/OpenHands/software-agent-sdk) | 将模型、工具、会话、执行环境拆开；支持本机和临时隔离环境 | 保持执行器可替换，避免调度、网页和模型调用挤在同一个大模块里。采用 SDK 前需单独核对认证与计费，不能假设它自动使用 Codex Pro 登录 |

## 最重要的共同经验

长任务不能只靠“再给 AI 发一句继续”。Anthropic 的[早期实验](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)使用功能清单、逐项实现和交接记录衔接多次会话；其[后续实验](https://www.anthropic.com/research/harness-design-long-running-apps)进一步将规划、生成和评价分开，让独立评价反馈驱动返工。后者也说明模型自我打分容易过于宽松，评价标准需要校准。

对 AgentBoard 的建议由此推导而来：把交付拆成可验证的小步，让检查结果决定下一步；保留工作状态和证据；换会话时携带结构化交接；只有需要用户判断的取舍才打扰用户。同一个模型分开会话有助于隔离职责，但不能消除相同模型的共同盲点，因此确定性的程序检查仍不可缺少。

## AgentBoard 当前缺口

本地已有隔离副本、任务依赖、范围和保护文件检查、超时停止、简单规则验收、任务胶囊、显式接入和受保护撤回。这些是可沿用的基础。

持续自主推进尚未形成完整闭环：

- 当前开发任务启动一次执行器，检查后进入 review、decision 或 blocked；检查失败没有自动组织修复与重新审查。
- Codex 使用 `exec --ephemeral`，不能把当前任务的持久会话接续能力视为已实现。
- 重启时把活动记录标为中断，不是从已保存步骤自动恢复。
- Python 自动检查支持语法编译和简单文件规则，还没有通用的项目测试计划、浏览器验收和独立审查阶段。
- 没有系统化的“连续无进展”识别，也没有任务级总尝试次数和跨会话累计时长控制。
- 当前主要交付物需要阅读技术细节；非专业用户需要更清楚的“做了什么、证据在哪、我是否需要决定”。

## 第一阶段 让一个任务自己完成返工

用户流程保持简单：说目标 → 确认验收方式 → 开始自主执行 → 查收结果。

内部流程设计为：

1. 规划：生成小任务、允许修改范围、验收标准和停止条件。
2. 实现：Codex 在隔离工作区修改代码。
3. 程序验收：Python 运行预先约定的测试，不采信执行器自己写的“通过”文字。
4. 独立审查：另一 Codex 会话针对目标和差异找缺陷，给出具体问题与证据。
5. 返工：未通过的检查和审查问题回到实现步骤；保存每一轮差异及结果。
6. 交付：检查通过后展示结论和证据，按项目事先选择的接入政策处理。

建议首版保留单次尝试最多 25 分钟，另设任务累计时长和返工次数，例如最多三轮。连续两轮出现相同失败且没有有效改动时，换方法或提出具体卡点。次数是初始配置建议，尚未写成当前应用行为。

日常局部编辑、运行测试和重试可自动完成；发布、会改变数据格式的迁移、删除重要内容和扩大修改范围应进入事先明确的项目政策。暂停、停止和拒绝必须是调度器状态，不能仅靠提示词约束。

第一阶段验收应包含：故意提供一次失败的实现，程序能够识别失败、携带失败证据启动修复，并最终通过固定测试；人为损坏测试文件不能绕过验收；停止后不再派生新的尝试。

## 第二阶段 让它关闭后还能接着干

将任务、尝试、检查、审查和事件分开记录，采用 SQLite 事务保存领取状态和检查点；重启后先核对真实进程和工作区，再决定恢复或重跑，避免重复执行。记录目标版本、代码基线、检查命令、退出码与证据文件哈希。

[LangGraph 的持久化](https://docs.langchain.com/oss/python/langgraph/persistence)区分当前工作状态与跨任务记忆；[Temporal 的持久执行](https://docs.temporal.io/ai)提供故障后接续的工程思路。对于目前的单机应用，优先判断标准库 SQLite 和独立调度模块是否足够；不要只为追求高级而引入额外服务。若未来确实需要复杂分布式执行，再比较框架的总维护成本。

Codex 适配器可逐步采用官方 [app-server 协议](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md)，获取结构化会话和执行事件，减少解析自然语言日志。具体字段必须按已安装版本验证，不能把最新主分支文档当作本机能力保证。

## 第三阶段 让交付容易看懂并能规模化

- 为每个项目保存可复用的启动、测试、浏览器和人工验收步骤；截图应对应具体验收项。
- 独立任务再启用少量并行工作区，约束哪些文件可同时修改；共享文件或接口变更按依赖串行。
- 首页优先显示当前目标、实际进度、卡点、检查证据与用户需要做的决定。
- 用干净安装环境测试启动器、执行器发现、升级和回退，再建设公开发行包。

“业界顶尖”需要持续测量，不能靠 Agent 数量或功能名称判断。建议建立固定的二十项试验集，涵盖功能实现、修复、界面、依赖、超时、重启和虚假完成。每次版本记录任务成功率、人工介入次数、错误报完成次数、恢复成功率、越界改动及完成时间。二十项是建议的基准规模，本轮没有声称已经完成这些评测。

## 本轮实际落地

已实现并离线验证：按账号真实额度窗口执行 Codex 保护；支持只有周窗口的账号；五小时字段缺失时保持空值；任务和聊天采用同一判断；保留 15% 阈值、时效检查与失败拦截；中英界面显示真实窗口。

已真实试跑：通过 AgentBoard 调用 ChatGPT 登录的 Codex CLI，在独立示例工作区修复任务依赖判断。固定八项测试先有四项失败，修复后八项通过；额外 Python 观察与验收脚本独立复测通过。测试文件、说明和原项目哈希未变，结果留在待查收阶段，没有自动接入。

这证明单任务执行与独立验收链路可用。它不证明长时间无人值守、自动返工、断点恢复或复杂项目质量已经达到目标；上述阶段仍是后续实施路线。本轮未提交或发布到远端。
